## 实验设计与实现

`scripts/benchmark_accelerators.py` 提供独立性能入口，直接调用项目现有模型、预处理、
五种归因适配器及 MoRF 函数。每个进程只看见一张指定卡，每个进程写独立目录，
父进程核对完整图片覆盖与唯一 `(image_id, repeat)`，最后才生成成功汇总。
失败或超时保留日志和 `failure.json`，并终止本次子进程。

所有实验使用真实冻结 debug 图片、ImageNet 官方预训练权重、FP32 和固定 seed。
兼容性冒烟检查为三模型 × 五方法，每项一张图，包含归因有限性、float32 NPY 和 21 点
raw MoRF。固定工作量的吞吐对照使用同一批 16 张 ImageNet debug 图，比较一卡串行
与八卡分片，既不减少样本，也不减少归因采样数。

- KernelSHAP：7×7 特征网格，2048 个样本，batch 16；再测试 batch 128。
- RISE：4000 个掩码，7×7，p=0.5，batch 32；并发对照保持 batch 不变。
- IG：50 步 Gauss–Legendre，internal batch 10。
- Occlusion：15×15 窗口、8×8 步幅，perturbations per eval 16。

每个 worker 至少预热一次，所有 worker 就绪后通过共同的启动屏障开始计时。
`steady_wall_seconds` 为最早开始至最晚完成的墙钟时间，包括测量期内图片上卡、归因、
NPY 保存，以及门禁所选 MoRF；`total_wall_seconds` 另外包含进程启动、导入、模型加载、
预热和协调开销。归因计时前后均同步设备。CPU 线程/BLAS 线程限制为每进程 2。

不能将这些 debug 性能实验混入 460 张正式 eval 或不同硬件的方法效率排名。
本分支的 RISE 适配器内部使用 softmax，因此此次 RISE 基准限定 ImageNet，程序会拒绝
VOC RISE；VOC 多标签语义应先与 C 的实际实现统一。此次不改动冻结的科研结果或采样协议。

## 实测结果

全部 23 组实验成功，合计 815 次测量归因、815 张 NPY，包含 15 组兼容性检查、
6 组固定工作量对照、64 次短负载和 640 次持续负载。没有 CPU 回退或失败的 worker。
三模型 × 五方法均能执行归因和 21 点 MoRF；这是一图兼容性检查，不替代正式科研门禁。

下面均为 ResNet50 / ImageNet，同一批 16 张冻结 debug 图片，采样预算不变。
“计算阶段”采用上文 steady 定义，吞吐对照未包含 MoRF 或稳定性扰动。

| 方法及 batch | 单卡计算阶段 | 八卡计算阶段 | 计算加速比 | 单卡总耗时 | 八卡总耗时 | 总耗时加速比 |
|---|---:|---:|---:|---:|---:|---:|
| KernelSHAP 2048，batch 16 | 34.755 s | 4.496 s | 7.730× | 65.481 s | 36.566 s | 1.791× |
| KernelSHAP 2048，batch 128 | 30.528 s | 3.804 s | 8.026× | 60.281 s | 35.769 s | 1.685× |
| RISE 4000，batch 32 | 34.921 s | 4.377 s | 7.978× | 63.782 s | 35.068 s | 1.819× |

八卡按图片分片能够接近线性扩展；8.026× 略高于 8 属于小样本单轮运行波动，
不能解释为超线性收益。每次重新启动 worker 有约 29–32 秒的导入、模型加载、
预热和协调开销，所以小任务的端到端加速只有约 1.7–1.8×。正式批量执行应让
各卡 worker 持续处理其图片分片，避免每张图或很小批次重新启动解释器。

KernelSHAP 的 batch 16 → 128，在单卡同工作量下吞吐提高 13.85%；
八卡同工作量下由 3.559 提高至 4.206 次/秒。增大 batch 有收益，但远小于八卡分片。

持续负载使用同一批 16 图重复 40 次，共 640 次解释，每卡 80 次，并非 640 张独立图：

- 计算阶段 154.812 秒，含启动总耗时 185.954 秒，吞吐 4.134 次/秒。
- 每次解释平均 1,901.443 ms、中位数 1,881.044 ms。
- 最大单卡 PyTorch allocated 峰值 1,683,052,544 字节，约 1.57 GiB。
- 八张卡的采样利用率峰值都达到 100%；持续负载监控记录最高 62°C、366 W/卡。
  完整实验（含模型切换及各方法）监控最高 68°C、549 W/卡。
- 利用率随前向计算、CPU 回归和保存阶段变化，不能声称八卡始终 100%，
  也没有把显存占满。此处是实际项目负载测试，不是长时间硬件烧机。

这是同一台 DCU 的单卡/八卡扩展性结果，尚无相同协议、环境与样本的 NVIDIA
对照，不能据此声称比团队现有显卡快多少。当前持续阶段约 2.6 分钟，尚不能证明
数小时运行稳定性，完整 460 图评估也未在此次实验中重跑。

## 独立核验与数值差异

下载后重新读取每个 worker 的结果和全部 NPY，独立重算覆盖、重复键、文件哈希、
float32 / 224×224 / 有限性、计时和吞吐汇总，23 组全部通过。
核验器也用破坏过的临时 NPY 验证过，确实拒绝哈希不符的结果。
八个 worker 的 HIP/CUDA 可见设备分别是 0–7，每个 worker 仅看到一张卡。

| 逐图对照 | 最大绝对差 | 最低 Spearman |
|---|---:|---:|
| KernelSHAP batch 16，单卡 / 八卡 | 0 | 1.0 |
| KernelSHAP batch 128，单卡 / 八卡 | 0 | 1.0 |
| RISE，单卡 / 八卡 | 0 | ≈1.0 |
| KernelSHAP，batch 16 / 128 | 1.5050e-6 | 1.0 |
| CPU / DCU Grad-CAM，同一张图 | 3.2783e-7 | 0.99999998 |
| CPU / DCU IG，同一张图 | 0.00692284 | 0.99995788 |

CPU 参照使用本地 PyTorch 2.14.0+cpu / torchvision 0.29，而 DCU 为厂商 2.10 / 0.25，
所以只作为数值检查，不能分离框架版本和硬件的影响，也不作硬件速度排名。
IG 的 MoRF AUC 为 CPU 0.0226873、DCU 0.0214233，存在可测差异；正式跨硬件复用
结果前仍应固定软件栈、执行完整门禁。单卡与八卡结果一致性不受这个跨栈问题影响。
